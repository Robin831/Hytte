- **Macro plan generation, validation and persistence** - New `GenerateMacroPlan` in `internal/stride/macro.go` ties the macro pieces together into one call: it snaps the requested start to its Monday, checks that Stride and Claude are both enabled, assembles the athlete inputs with `buildMacroInputs`, pairs them with the macro instruction block, calls Claude through the existing `runPromptFunc` seam under a 300s timeout mirroring the coach-evaluation path, decodes the answer into `MacroPlanResponse`, runs `ValidateMacroPlan` against the same horizon, weekly distance cap and race calendar the prompt was built from, and only then writes the block. Validation deliberately runs before the write, so a rejected plan leaves no plan row, no weeks and no goal history behind, and the whole block plus its `initial` goal revision land in `CreateMacroPlan`'s single transaction. The generation mode decides both the prompt and what the block is recorded as: extension mode seeds the prompt with the block that is running out so training continues instead of restarting from base, and fails fast with `ErrNoPreviousMacroPlan` when there is nothing to continue rather than quietly planning a fresh block under the extension label; scheduled and manual mode replace whatever active block already covers the start week. In every mode the block being followed is recorded as `previous_plan_id` and retired in the same write, so the athlete is never left with two active blocks on one Monday or with none at all. The weekly and macro generators now share one default-model constant, so a block is never planned on a cheaper model than its weeks. Nothing schedules or exposes this yet — the cron and the API surface land separately. (Hytte-go5pg)
