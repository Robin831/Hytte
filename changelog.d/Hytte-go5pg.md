- **Macro plan generation, validation and persistence** - New `GenerateMacroPlan` in `internal/stride/macro_generate.go` ties the macro pieces together into one call: it snaps the requested start to its Monday, checks that Stride and Claude are both enabled, assembles the athlete inputs with `buildMacroInputs`, pairs them with the macro instruction block, calls Claude through the existing `runPromptFunc` seam under a 300s timeout mirroring the coach-evaluation path, decodes the answer into `MacroPlanResponse`, runs `ValidateMacroPlan` against the same horizon, weekly distance cap and race calendar the prompt was built from, and only then writes the block. Validation deliberately runs before the write, so a rejected plan leaves no plan row, no weeks and no goal history behind, and the whole block plus its `initial` goal revision land in `CreateMacroPlan`'s single transaction. The generation mode decides both the prompt and what the block is recorded as: extension mode seeds the prompt with the block that is running out so training continues instead of restarting from base, and fails fast with `ErrNoPreviousMacroPlan` when there is nothing to continue rather than quietly planning a fresh block under the extension label; scheduled and manual mode replace whatever active block already covers the start week. In every mode the block being followed is recorded as `previous_plan_id`, and every active block the new 26-week horizon overlaps — including one that starts after the new block does, the shape a scheduled extension leaves behind — is retired in the same write, so the athlete is never left with two active blocks covering one week or with none at all. `CreateMacroPlan` re-checks which blocks are active inside its own transaction rather than trusting the id the caller resolved minutes earlier, so a second generation racing the first is rejected with `ErrOverlappingMacroPlan` instead of leaving two active blocks covering the same weeks. The weekly and macro generators now share one default-model constant *and* one way of applying it — keyed off the athlete's `claude_model` preference rather than the already-defaulted config — so Stride planning falls back to the model that constant names instead of the cheaper package-wide default. Both response parsers also share one code-fence stripper, which now keeps the last line of an answer whose closing fence never arrived. Nothing schedules or exposes this yet — the cron and the API surface land separately. (Hytte-go5pg)
